# M9-3 통합 부하 테스트 결과 (수강신청 시나리오)

## 목적
실제 유저 흐름 전체(로그인 → 강의목록 → 수강신청 → 시간표)를 진짜 JWT 인증으로
동시 부하 걸어, 정원 30 강의에 100명이 몰릴 때 **오버부킹/언더부킹이 없는지** 검증.

## 시나리오 (`load-test/scenarios/enrollment.js`)
- 유저 100명(`loaduser_1~100`) Keycloak 로그인 → 토큰 사전 확보 (측정 구간에서 Keycloak 병목 제거)
- 각 학생: `GET /api/courses` → `POST /api/enrollments` → `GET /api/timetable`
- 대상 강의 id=9001, 정원 30으로 매 실행 전 DB 리셋 (`run.sh`)
- k6 threshold로 오버부킹(성공>정원)·서버에러(500) 발생 시 자동 FAIL

## 발견 → 개선
| 구분 | enroll_success | 결과 |
|------|----------------|------|
| 재시도 없음 (1회 시도) | **7 / 30** | 언더부킹 — 23자리 빔 |
| 재시도 있음 (LOCK_BUSY 재시도) | **30 / 30** | 정원 완전 충족 |

**원인:** 분산 락 `WAIT_TIME=3초`. 100명이 같은 강의 락에 몰리면 3초 안에
락을 못 잡은 요청은 `LOCK_BUSY(409)`로 빠르게 튕김(= 의도된 부하 차단).
1회만 쏘는 테스트에선 이게 언더부킹처럼 보임.

**개선:** `LOCK_BUSY`는 "다시 시도" 신호. 실제 수강신청도 학생이 새로고침하며 재시도함.
k6에 재시도 로직 추가(백엔드 무수정) → 정원만큼 정확히 충족, 오버부킹은 여전히 0.

## 최종 지표 (재시도 적용)
- enroll_success = **30**, enroll_full = **70**, enroll_error = **0**
- lock_retry_total = 139 (락 경쟁 강도)
- http_req_failed = 0%, threshold 전부 통과, DB 최종: enrolled=30 / remaining=0

## 결론
- **오버부킹 0** — DB 비관적 락(SELECT FOR UPDATE)이 최종 방어선으로 정확히 동작
- **언더부킹 0** — 클라이언트 재시도로 정원 완전 활용
- `WAIT_TIME`은 부하 차단 강도 조절 노브: 짧을수록 빠른 실패(꼬리지연↓, 재시도 의존),
  길수록 대기 후 성공(꼬리지연↑). 현재 3초는 재시도 전제 하에 적절.
