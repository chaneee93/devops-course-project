# M4-4 부하 테스트 결과 (동시성 제어 Before/After)

## 테스트 조건
- 도구: k6 (shared-iterations, VU 50, 총 50 요청)
- 대상: 정원 10명짜리 강의에 50명 동시 수강신청
- 환경: 로컬 (Docker MySQL 8.0 + Redis 7)

## 결과 요약

| 항목 | BEFORE (락 없음) | AFTER (락 있음) |
|---|---|---|
| 정원 | 10 | 10 |
| 실제 등록 수 | **50 (정원 초과!)** | **10 (정확)** |
| overbooked | true | false |
| 신청 성공 | 50 | 10 |
| 신청 거절(409) | 0 | 40 |
| 응답시간 avg | 680ms | 1.18s |
| 응답시간 p95 | 967ms | 1.69s |
| 진짜 에러(5xx) | 0 | 0 |

## 해석
- **BEFORE**: 락이 없어 race condition(lost update) 발생 → 50명 전원 등록되어 정원 초과.
  잔여석(remaining)과 실제 등록 수가 불일치하며 데이터 정합성이 깨짐.
- **AFTER**: Redis 분산 락(1차 필터) + DB 비관적 락(정합성 보장)으로
  정확히 정원(10명)만 성공, 나머지 40명은 409로 정상 거절.
- **트레이드오프**: 락으로 인해 평균 응답시간이 증가하나, 정합성을 확보함.

## 사용한 동시성 제어 (M4-1 ~ M4-3)
- M4-1: DB 비관적 락 (SELECT ... FOR UPDATE)
- M4-2: Redis 분산 락 (Redisson RLock, DB 락 앞단 1차 필터)
- M4-3: 시간 중복 신청 방지
